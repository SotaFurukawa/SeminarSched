# Phase 2 手動確認手順

この手順はWindows上でPhase 1の起動基盤を回帰確認し、Phase 2のプロジェクト管理、
マスターCRUD、コマ・開校日設定、Excel基本入出力を確認するためのものである。

実在する生徒・講師・校舎の情報は使用しない。ここに記載した名前はすべて架空である。
アンケート本取込み、集団授業、最適化、時間割編集、PDFは確認対象に含めない。

## 1. 前提と隔離した確認領域

READMEの手順でPython 3.12の仮想環境と開発依存関係を準備する。普段使用している
アプリ管理DBやログに触れないよう、同じPowerShellプロセス内だけ保存先を一時
ディレクトリへ変更する。

```powershell
$manualRoot = Join-Path ([System.IO.Path]::GetTempPath()) ("SummerSchedulerPhase2-" + [guid]::NewGuid().ToString("N"))
New-Item -ItemType Directory -Path $manualRoot
$env:SUMMER_SCHEDULER_DATA_DIR = Join-Path $manualRoot "data"
$env:SUMMER_SCHEDULER_LOG_DIR = Join-Path $manualRoot "logs"
$projectPath = Join-Path $manualRoot "日本語確認_2026夏期講習.jukuschedule"
python -m summer_scheduler
```

PowerShellを閉じると、このプロセスに設定した環境変数は失われる。確認用ファイルを
削除する場合は、アプリを終了し、`$manualRoot` がこの手順で新規作成したディレクトリ
であることと内容を目視確認してから行う。

## 2. Phase 1の回帰確認

1. ウィンドウタイトルが「夏期講習時間割作成」であることを確認する。
2. サイドバーに次の9項目が表示されることを確認する。
   - ホーム
   - 生徒
   - 講師
   - 集団授業
   - アンケート取込み
   - 時間割
   - 未配置・警告
   - 出力
   - 設定
3. 「集団授業」「アンケート取込み」「時間割」「未配置・警告」「出力」が、対応する
   後続Phaseを明示したプレースホルダーであり、動作済みのように見せないことを
   確認する。
4. `$env:SUMMER_SCHEDULER_DATA_DIR\summer_scheduler.db` と
   `$env:SUMMER_SCHEDULER_LOG_DIR\summer_scheduler.log` が作成されることを確認する。
5. リポジトリ直下へDB、ログ、Excel出力が作られていないことを確認する。

## 3. プロジェクトの新規作成と再読込み

1. 「ホーム」→「新規プロジェクト」を開く。
2. 次を入力して作成する。

   | 項目 | 確認値 |
   |---|---|
   | 年度 | 2026 |
   | 講習区分 | 夏期 |
   | 開始日 | 2026-08-01 |
   | 終了日 | 2026-08-07 |

3. プロジェクト名が`2026夏期講習`へ自動設定され、保存先を尋ねず管理フォルダーへ
   `.jukuschedule`として作成されることを確認する。
4. 作成後、ヘッダーとホームに自動設定されたプロジェクト名と期間が表示されることを
   確認する。
5. アプリを終了して再起動し、「最近使用したプロジェクト」から同じファイルを開く。
6. 登録した内容が保持され、最近使用した一覧の先頭へ移動することを確認する。
7. `.jukuschedule` ではないファイルを「開く」で選択した場合、有効なプロジェクト
   ではない旨の日本語エラーが表示され、現在のプロジェクトを壊さないことを確認する。

## 4. プロジェクト情報とファイル操作

1. 「設定」→「プロジェクト」で、年度、講習区分、開始日、終了日を変更し、
   「変更を保存」を押す。プロジェクト名も選択内容から自動更新されることを確認する。
2. 終了日を開始日より前にすると、入力欄付近または状態バナーにエラーが表示され、
   保存されないことを確認する。
3. 期間を2026-08-01～2026-08-10へ延長し、新しい日付のOpenDateが追加されることを
   「開校日・休校日」で確認する。短縮した場合は期間外の日が一覧に残らないことも
   確認する。
4. 「ホーム」→「名前を付けて保存」で、日本語名の別ファイルへ保存する。表示中の
   プロジェクトパスが新しいファイルへ切り替わることを確認する。
5. 「複製」で別ファイルを作り、現在開いているファイルが切り替わらないことを
   確認する。
6. 「バックアップ」で別ファイルを作り、元のファイルを開いたままであることを
   確認する。
7. 編集フォームに未保存の変更を残して「閉じる」または別ファイルを開く操作をし、
   確認ダイアログが表示されることを確認する。キャンセル時は元のプロジェクトを
   開いたままにする。

作成された別名保存、複製、バックアップを順に開き、有効なプロジェクトとして同じ
登録内容を読み込めることも確認する。

## 5. コマ設定

「設定」→「コマ設定」で、作成直後に次の5件がこの順で表示されることを確認する。

| コマ | 開始 | 終了 | 順序 |
|---|---|---|---:|
| Y | 14:10 | 15:30 | 1 |
| Z | 15:40 | 17:00 | 2 |
| A | 17:10 | 18:30 | 3 |
| B | 18:40 | 20:00 | 4 |
| C | 20:10 | 21:30 | 5 |

次を1件ずつ入力し、保存が拒否され、どの項目が原因か日本語で分かることを確認する。
各確認後は値を元に戻す。

- 既存と同じコマ名
- 既存と同じ順序
- 開始時刻と終了時刻が同じ
- 開始時刻が終了時刻より後
- 他コマと重なる時刻区間
- 空のコマ名または表示名
- `25:00` や任意文字などの不正時刻

正常なコマの追加・編集・使用停止・削除も確認する。コマの連続・空き判定に
`sort_order`を使うという説明が画面に表示されることを確認する。

## 6. 開校日・休校日

1. 「設定」→「開校日・休校日」で、講習期間内の日だけが表示されることを確認する。
2. 「期間内をすべて開校」を実行し、全日が「開校」の文字でも判別できることを
   確認する。
3. 曜日を選び「指定曜日を休校」を実行し、該当曜日だけが休校になることを確認する。
4. 日付を1件選択し、休校、備考「架空の休校日」を保存する。
5. 同じ日を開校へ戻し、備考も更新できることを確認する。
6. 状態が色だけでなく「開校／休校」の文字で示されることを確認する。

## 7. 科目マスター

「設定」→「科目」で、初期科目が26件であることを確認する。

- 小学校: 7件
- 中学校: 5件
- 高校: 14件

小学校の算数・国語が中学受験とそれ以外に分かれ、高校数学IA・数学IIBC・数学IIIが
別の科目コードで存在することを確認する。片方を講師の指導可能科目にしても、他方が
自動選択されないことを後述の講師画面で確認する。

架空科目を追加・編集・並べ替え・使用停止できることを確認する。既存コードと同じ
科目コードはエラーになり、使用停止しても既存の受講希望と講師資格が削除されない
ことを確認する。

## 8. 生徒管理

1. 「生徒」→「生徒を追加」で次を登録する。

   | 項目 | 確認値 |
   |---|---|
   | 生徒ID | S-001 |
   | 氏名 | 架空 花子 |
   | 学年 | 中2 |
   | 標準最大連続コマ数 | 2 |
   | 空きコマ許可 | いいえ |
   | 備考 | 手動確認用の架空データ |
   | 有効 | はい |

2. IDまたは氏名の一部分で検索し、`S-0`、`花子`のどちらでも見つかることを
   確認する。
3. 学年フィルターとID順・氏名順・学年順の並べ替えを確認する。
4. 同じ`S-001`を追加するとID重複エラーになることを確認する。
5. 別ID`S-002`、同じ氏名「架空 花子」を追加し、同姓同名の警告が表示されることを
   確認する。警告はID確認を促し、同姓同名だけを理由に保存不能にはしない。
6. 基本情報を編集し、キャンセルで変更前へ戻ることを確認する。
7. 使用停止時と削除時に確認ダイアログが表示されることを確認する。
8. 受講希望を持つ生徒を削除する場合、依存する受講希望も削除される旨を確認した
   上でのみ実行されることを確認する。

## 9. 講師と指導可能科目

1. 「講師」→「講師を追加」で`T-001`、氏名「架空 太郎」、空きコマ許可「いいえ」
   を登録する。
2. ID・氏名の部分一致検索、ID順・氏名順の並べ替え、編集、キャンセルを確認する。
3. 同じ講師IDがエラー、別IDの同姓同名が警告になることを確認する。
4. 「指導可能科目」で学校段階を絞り込み、小学校・中学校・高校を個別に折りたたみ
   でき、科目コード・科目名・指導可否が表示されることを確認する。
5. 表示中の全選択、全解除、変更保存、キャンセルを確認する。
6. 別の架空講師を追加し、資格の一括コピーを確認する。
7. 「高校・数学IA」だけを選択して保存し、「高校・数学IIBC」と「高校・数学III」が
   未選択のままであることを確認する。
8. 講師を使用停止すると、新しい受講希望の通常担当・希望講師候補として選択できない
   ことを確認する。
9. 講師削除前に確認が表示され、削除後は資格が孤立せず、既存受講希望そのものは
   削除されず講師参照だけが解除されることを確認する。

## 10. 受講希望

生徒`S-001`と講師`T-001`を有効にし、`T-001`へ「中学校・数学」の資格を設定して
から、「生徒」→「受講希望」で次を確認する。

1. 中学校・数学、必要授業回数4、通常担当`T-001`、優先度3を登録する。
2. 必要授業回数0はエラーになる。
3. 優先度は1～5だけを選べる。
4. 優先度5で通常担当講師を未選択にするとエラーになる。
5. 優先度5の通常担当講師が対象科目を指導不可の場合はエラーになる。
6. 優先度1～4の通常担当講師が指導不可の場合は、警告を確認した上で保存できる。
7. 同一生徒・同一科目をもう1件登録すると重複エラーになる。
8. 第1～第3希望に同じ講師を重複指定すると警告が表示される。
9. 1対1必須、最大連続コマ数上書き、空きコマ許可上書き、備考を保存・再読込み
   できる。
10. 受講希望の削除前に確認ダイアログが表示される。

優先度5は将来の最適化におけるハード制約である。一方、優先度1～4と第1～第3希望は
将来のソフト制約であり、このPhaseでは入力と検証だけを行う。

2. Excelで開き、次の5シートがこの順で存在することを確認する。
   - 生徒
   - 講師
   - 科目
   - 講師対応科目
   - 通常授業
3. 各シートの1行目が日本語ヘッダーで、ヘッダーが固定され、フィルター、列コメント、

4. 「講師対応科目」「通常授業」で名前・科目名を選ぶと、隣のID・科目コードが自動表示
   されることを確認する。新規テンプレートに「（確認）」列がないことも確認する。
5. 「通常授業」は優先度`3`、1対1必須`いいえ`、「講師対応科目」は指導可能`はい`が

6. 「作成した基本情報を反映…」で反映し、「反映済みの基本情報を開いて編集」から共通正本を
   開けること、取込み前の正本が`基本情報バックアップ`へ保存されることを確認する。

## 12. Excelプレビュー、正常取込み、全体拒否

出力したブックをコピーして、実在人物と無関係な次の行を追加する。

- 生徒: `S-XLSX`、`架空 一郎`、`高1`
- 講師: `T-XLSX`、`架空 講師`
- 講師対応科目: `T-XLSX`と高校・英語を指導可能
- 受講希望: `S-XLSX`と高校・英語、必要回数2、通常担当`T-XLSX`、優先度3

「取込みファイルを選択」でブックを選び、DB反映前に次を確認する。

- シート・行番号・列名付きの検証結果
- シートごとの新規／更新件数
- 警告件数とエラー件数
- プレビュー前にはDB一覧へ新しい行が追加されていない

エラー0件であることを確認して「プレビュー内容を反映」を押し、生徒、講師、資格、
受講希望がすべて追加されることを確認する。同じファイルを再度プレビューすると、
該当行が新規ではなく更新として数えられることを確認する。

次に別コピーへ、正常な新規生徒1行と「優先度5・通常担当講師ID空欄」の不正な
受講希望1行を入れる。プレビューにエラーの行番号・「通常担当講師ID」が表示され、
反映操作が拒否されること、正常に見える新規生徒も部分反映されないことを確認する。

反映途中の例外に対するtransaction rollbackそのものは、UIから意図的にDB障害を
発生させず、自動テスト`tests/integration/test_master_excel.py`で確認する。

## 13. 画面サイズ、操作性、状態表示

1. 1366×768、Windows表示倍率100%で主要な追加・編集・保存・キャンセルを操作
   できることを確認する。
2. 表示倍率150%でも日本語ラベルが欠けず、長い一覧をスクロールできることを
   確認する。
3. 生徒・講師一覧が長くても入力中にUIが長時間固まらないことを確認する。
4. 状態が色だけでなく「有効／停止中」「開校／休校」「保存済み／未保存」
   「警告／エラー」等の文字でも判別できることを確認する。
5. Tab、Shift+Tab、Enter、Spaceで主要な入力欄、ボタン、チェックボックスを操作
   でき、フォーカス位置が分かることを確認する。

## 14. 確認後

アプリを終了し、ログに技術エラーがないことを確認する。ログ、DB、
`.jukuschedule`、`.xlsx`には個人情報が含まれ得るため、issue、Pull Request、
CI artifactへ添付しない。

確認用ファイルを残す必要がない場合は、`$manualRoot` がこの手順で作成した一時
ディレクトリであることを再確認してから削除する。実運用ファイルや既存の
`%LOCALAPPDATA%\SummerScheduler`をこの手順のcleanup対象にしない。
